## Cross-cutting behavior

- Collector registry is the `COLLECTORS` mapping in `v2/radar.py`.
- Scheduler runs independently by source in a single FastAPI process; a source's own `running` guard skips overlapping runs.
- A source run stores `jobs_seen`, `new_jobs`, start/finish and an error in `source_runs`.
- Shared pipeline: normalization, source ID upsert, canonical opportunity assignment, deterministic match evaluation, notification decision and Telegram.
- Telegram uses a durable notification ledger with retry state.
- SQLite tables: `jobs`, `canonical_opportunities`, `job_evaluations`, `notification_ledger`, `source_runs`, and optional `gemini_shadow_cache`.

## Known observability mismatch

The collector registry contains Ashby, but source enumeration in three endpoints is hard-coded without it:
- `GET /api/source-status`
- `GET /api/latency-summary`
- `GET /api/dedupe-candidates`

The endpoints must derive their source set from the same registry to prevent future drift. Add regression tests for every registered source.
